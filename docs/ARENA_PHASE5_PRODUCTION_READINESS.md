## 2. Proposed pilot operating model — owner decisions required

The owner nominated the first host and selected the proposed pilot window and audience cap. These are planning decisions, not production activation authorization. Remaining operational and safety choices require owner approval:

- **Hosts:** the owner nominated `admin@orbace.com` as the first host. Verify the account and obtain its authenticated Orbace `sub` privately; do not configure the production allowlist without separate authorization. A backup host is not selected. The Phase 4 throwaway host was deleted and must not be reused.
- **Window and audience:** the owner selected one supervised 60-minute window with up to 20 invited viewers, unranked, no public launch. Owner/PM must choose the actual date, channel, consent/privacy notice and staffing. This is not proof of capacity; run an approved load test for the chosen cap.
- **Supply:** Extreme-only private puzzles; Quick/Standard/Endurance select time modes, not difficulty. Select a licensed, owner-approved bank large enough for the agreed number of rounds/rematches and repeat window. No repeat within a series; exhausted or protected/colliding supply fails closed. The staging set supplies evidence, not automatic production approval.
- **Fairness:** guest voting uses browser credentials and rate controls, not verified one-person-one-vote. PM must explicitly choose a mitigation or accept the vote-stuffing risk; validate trusted proxy/client-IP behavior before setting rate limits. See `docs/issues/ARENA-ISSUE-001-guest-vote-stuffing.md` and `ARENA-ISSUE-002-small-puzzle-bank.md`.
- **Staffing:** name an operator monitoring the deployment, an incident lead, a database owner and an authorized kill-switch operator with a tested communication path. The host nomination did not separately identify who may activate the kill switch; confirm that authority before release. No production access is assumed here.
- **Proposed abort triggers:** any leaked answer/private identifier, unauthorized host control, protected-puzzle selection, duplicate/conflicting terminal outcome, incorrect deadline/winner, or critical production/Zero-Tap regression triggers immediate stop. Proposed operational threshold: error rate above 1% of at least 20 Arena requests in five minutes, or p95 Arena latency above two seconds for five minutes, prompts a stop/investigation. These figures require owner/operations approval and instrumentation before use; they are not existing alert thresholds.

## 3. Staged production change plan — execute only after separate owner authorization

1. **Freeze/reconcile.** Independently review this plan. Reconcile the approved integration with current application main in an isolated worktree, preserve unrelated work, review the full diff, resolve test isolation, obtain an approved immutable source/build identity, and secure explicit commit/push/merge/deployment authorizations. Verify production and Preview targets and obtain a tested backup/recovery point with the DB owner. Do not put connection strings into commands, logs or review evidence.
2. **Resolve migration drift.** DB owner compares the production ledger and actual schema to the intended checked-in migrations, explains the checksum difference and rolled-back/completed records, checks the effects of historical manual resolution and documents a safe, independently reviewed path. Stop on unresolved failures, unexpected pending migrations or destructive SQL. Record the precise expected single Arena migration and approved RLS statements.
3. **Prepare schema safely.** With explicit production DB authorization, apply only the reviewed additive Arena migration using an approved migration process that fails closed on error. RLS must be enabled on all six new tables in the same transaction as creation. Verify migration result, unchanged existing data, RLS/policies/grants, ledger posture, all existing flows and health before exposing any table or continuing. Apply the idempotent Arena companion only as approved. No reset, general rollback/drop, or unrelated schema changes.
4. **Prepare supply and retention.** With owner authorization, validate licensed Extreme-only private puzzles and production collision checks, seed only explicitly eligible rows, and check public/overlay/host response and public puzzle-route opacity. Configure an approved <=7-day event retention and an owned scheduler/alert; separately document other Arena data retention and deletion. No logging of solutions, credentials, raw IP or guest identifiers.
5. **Deploy disabled.** Only after separately authorized publication/deployment, deploy a reviewed immutable backend and frontend with Arena off and allowlist empty until host authorization. Add the narrow same-origin route with regression coverage for challenge, Reddit Help to Solve, Su-Pu, rankings and existing API flows. Ensure migration failure blocks rollout; verify production health, flag-off 404, trusted proxy/origin/cookie/CSRF and privacy. Preserve production Vercel protection; do not create a broad bypass as a shortcut.
6. **Authorize host and run controlled pilot.** Require signed-off operating model, verified real host `sub`, capacity, supply, alerts, incident/kill-switch owners and explicit owner approval. Apply the smallest production host allowlist and flag change. Run the approved supervised journey and negative checks using authorized test identities; monitor thresholds and stop on any abort condition.
7. **Disable/restore.** The named operator turns `ARENA_ENABLED` off via the approved configuration method, verifies all instances and public routes, confirms 404/hidden controls and normal health, and records the impact on existing sessions. Do not assume disabling reverses data/schema. Use a reviewed forward fix or DB-owner-approved backup recovery; do not drop shared tables automatically. Remove pilot-specific access/data only under the approved retention and cleanup plan.
